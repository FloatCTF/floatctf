## 赛制一：Jeopardy（解题赛）

- 个人赛与团队赛两种模式。
- 静态 Flag 与动态 Flag。
- 动态积分衰减（分值随解题人数下降）。
- 题目实例按需启动（独立容器）。
- 实时计分板与得分趋势。
- Writeup 提交。
- 赛事公告。

## 赛制二：AWD（攻防对抗）

- 支持 2 队及以上的对抗赛事。
- 加固（hardening）与攻击（attack）分阶段。
- 选手通过 WireGuard 接入竞赛内网。
- nftables 作用域隔离。
- Flag 下发与提交。
- 一血（first blood）标记。
- 对称失分（symmetric loss）。
- 每轮结束判定（judge at end of round）。
- 暂停 / 恢复。
- 重置（带配额与罚分）。
- 封禁 / 解封（ban / unban）。
- 最终结算与 finished 锁定（final settlement / finished lockdown）。

## 赛制三：AWDP（攻防演练）

- 练习/训练 run 与正式竞赛两种形态。
- 破坏（break）与修复（fix）阶段。
- 正式轮次评测（official round evaluations）。
- 补丁提交（patch submission）。
- 分数账本（score ledger）。
- Writeup。

## helper 安全架构

- API 是 Compose 中的**非 root** 容器：`cap_drop: ALL`、`no-new-privileges`、
  read-only rootfs。
- API **不挂载 Docker socket**，也**不持有 `CAP_NET_ADMIN`**。
- 所有需要宿主特权的操作都经由 `floatctf-helper`，通过两个 Unix socket：
  - `helper-docker.sock`：Docker 策略代理（只放行受限操作）；
  - `helper-control.sock`：宿主 Host RPC。
- 宿主的 WireGuard / nftables 由 helper 独占管理。
- 宿主 `systemd` 只管理 `floatctf-helper.service` 与 Compose 生命周期
  （`floatctf-infra.service` / `floatctf.target`）；API 本身跑在 Compose 里，
  **没有** `floatctf-api.service`。

## 安装与部署

- `install.sh` **单文件自包含**：目标机无需 clone 源码。
- Compose 统一承载 API / PostgreSQL / Redis / RustFS / Caddy。
- Caddy 自动 HTTPS。
- 宿主 systemd 只负责 `floatctf-helper` + Compose stack。
- 迁移 forward-only；fresh DB 从 `merged.sql`（48 个迁移）bootstrap。
- 升级路径：重跑 `install.sh --version <V>`；既有 PostgreSQL 集群上先起 postgres、
  应用 forward-only 迁移，再部署。

## 可插拔前端平台

- `apps/web` 是极薄的 bootstrap 引导页；`frontends/default` 是官方前端；
  `packages/{sdk,react,frontend-runtime}` 是前端 SDK / 绑定 / 运行时契约。
- 前端制品**版本不可变**（资产以 `Cache-Control: public, max-age=31536000, immutable` 提供）。
- 通过动态设置 `FRONTEND_ACTIVE` 激活前端。
- 破窗恢复：任意页面追加 `?frontend=default`。
- 支持外部非 React 前端。

## 运维工具

- `backup.sh` / `restore.sh`：生产备份与恢复。
- 安全卸载（`uninstall.sh`）带**活跃运行时守卫**。
- `uninstall.sh --purge`：永久清除 FloatCTF 自有状态。
- `frontend.sh`：前端管理器（`list` / `info` / `install` / `remove` / `set-current` / `verify`）。
- `SHA256SUMS`：覆盖除自身外的全部发布产物。

### SDK 分发

- `floatctf-sdk-<V>.tgz`、`floatctf-react-<V>.tgz`、`floatctf-frontend-runtime-<V>.tgz`
  随每个 GitHub Release 附带，逐字节确定性；`scripts/package-sdk-dist.sh` 会在旁边写
  `SDK-SHA256SUMS`。
- **npm 尚未为 v1.0 执行发布，且属可选。** 已核实的细节：三个 tarball 一起安装时用
  **npm** 可用；用 **pnpm** 目前会失败（未发布的 `@floatctf/sdk` 触发
  `ERR_PNPM_FETCH_404`），这是 pnpm 对「相互依赖的未发布本地 tarball」的限制
  （已用通用场景复现）——因此 pnpm 消费者需要先把包发布到 registry。
- `@floatctf/react` 消费方 peer deps：`react@^19`、`react-dom@^19`、
  `@tanstack/react-query@^5.66.5`；`@floatctf/sdk` 依赖 `axios ^1.11.0`；
  `@floatctf/frontend-runtime` 无依赖。
- `packages/react/dist/index.d.ts` 需要 `skipLibCheck: true`（仓库内每个 tsconfig 都已设置）。

## 已知限制（Known limitations）

以下为**如实记录**的限制，不美化、不夸大：

1. **真实域名 HTTPS 未验证。** RC 环境没有域名/DNS/TLS，只验证了本地 Caddy
   internal-CA 链路（`curl --cacert`，未使用 `-k`）。
2. **AWD / AWDP 未执行完整宿主级 E2E（WireGuard / nftables）。** 平台 AWD 防火墙状态是
   **单一全局 nft 表**（`floatctf_awd`，练习用 `floatctf_awdp_practice`）加上固定命名的
   宿主资源（`fctf-awdp-practice`、`fctf-awdp-practice-judge`）。在已运行线上 FloatCTF
   实例的宿主上再起第二个 API 实例，会删除并重写这份全局状态。
   **同一宿主同一时刻只允许一个 FloatCTF API 操作 Docker daemon + helper。**
   实测后果：第二个（RC）API 曾重建线上练习 judge 与网络一次（约 23 秒窗口），
   随后被生产自身的 30 秒 cron 自愈。运维人员**不得**在正在服务线上赛事的宿主上运行
   第二套 API / dev stack。
3. **特权路径未端到端执行。** `floatctf-helper` 与宿主 group/systemd 配置需要 root；
   agent 环境为 `NoNewPrivs=1` 且无 `sudo`，因此全新安装 / purge / uninstall 的特权路径
   只做了审计与静态/功能测试，**未**端到端执行。
4. **Default Frontend bundle 约 4.3 MB（gzip 约 1.08 MB）**：v1.1 的优化候选，不是阻塞项。
5. **前端不支持无刷新热切换**（切换需要页面重载）；**没有**前端 Marketplace / 签名机制
   （post-v1.0）。
6. **AWD/AWDP 运行时镜像不随 release 分发**：`floatctf/awd-flagserver`、
   `floatctf/awd-judgeserver`、`floatctf/infra/awdp-judgeserver` 需要在**有源码的机器**上
   用 `sudo bash scripts/build-runtime-images.sh --tag <V>` 本地构建。对全新宿主上的
   AWD/AWDP 而言，这是**已知 GA 阻塞项**，在此如实说明。
