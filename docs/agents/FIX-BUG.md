# 修复 Bug（FIX-BUG.md）

> 原则：**先诊断、后修复、修复后必回归**。不要在没定位根因前乱改代码；涉及数据的修改先向用户确认。

## 流程总览

```
1. 复现 → 2. 分类定位 → 3. 根因分析 → 4. 最小修复 → 5. 回归测试 → 6. 提交
```

## 步骤 1：复现

- 收集报错原文（日志、panic 信息、HTTP 状态码），不要转述。
- 常用命令：
  ```bash
  mise run dev:api               # 看启动/运行日志
  mise run infra:logs            # 基础设施（nginx/db/rustfs）日志
  curl -s -o /tmp/r.txt -w "%{http_code}" http://localhost:7780/api/xxx
  ```
- 无法复现时，明确复现前置条件（数据状态、账号权限、配置项）。

## 步骤 2：分类定位

| 症状 | 优先排查方向 |
|------|-------------|
| 编译错误（E0425/E0599/E0560） | 实体与代码不一致 → 见下方"陷阱 A"；sea-orm-cli 版本 |
| 启动 panic（数据库/对象存储） | 基础设施未起（`mise run infra:up`）、TOML 配置错误、迁移未应用 |
| 启动 panic（SQL 列不存在） | Schema 漂移 → 见"陷阱 B" |
| 运行时 404 | 路由没在 `bootstrap/routes.rs` 注册；前缀错误 |
| 运行时 500 | handler 内 `AppError` 未正确映射；service 层 panic |
| Nginx 502 | 后端进程未起（API 9090 / Web 3000）；nginx 配置 upstream |
| 数据对不上/查询报错 | 三处不一致（实体/代码/DB）或 settings 表缺键 |

先跑编译与单元测试确认基线：

```bash
cargo check -p floatctf
cargo test -p floatctf
```

## 步骤 3：根因分析

### 陷阱 A：sea-orm-cli 版本不匹配
实体由 `scripts/gen_entities.py` 生成，**要求 sea-orm-cli 1.1.20**（与运行时 sea-orm 1.1.20 匹配）。
- 症状：`cannot find type Enum in this scope`（E0425，`rs_type = "Enum"` 语法）
- 检查：`sea-orm-cli --version`；实体文件头 `@generated by sea-orm-codegen X`
- 修复：`cargo install sea-orm-cli --version 1.1.20 --locked` 后重新 `mise run db:gen`

### 陷阱 B：实体 / 代码 / DB Schema 三处不一致（最常见、最隐蔽）
同名字段在三个地方状态不同：

| 位置 | 说明 |
|------|------|
| `apps/api/src/entity/*.rs` | 生成的"蓝图" |
| 业务代码 | 使用方（如 `Column::EventId`） |
| 数据库表 | 实际 Schema |

**排查顺序**：
1. `git diff apps/api/src/entity/` 看实体最近是否被重新生成（生成来源是 DB，DB 没列它就没了）
2. 对照迁移文件（`apps/api/src/sql/migrations/`）确认该列是否真的存在
3. 查实际库：`docker exec floatctf-dev-db psql -U postgres -d floatctf_db -c '\d 表名'`
4. 三处对齐：**以需求为准**（要么补迁移加列，要么删代码引用），再跑 `mise run db:gen`

> 历史教训：`challenge_solves.event_id` 只存在于旧实体和代码，迁移与库里都没有——启动时不查该表所以能跑，一旦查询立刻报错。**"能编译、能启动"不等于"数据一致"。**

### 陷阱 C：配置来源混乱
- 项目已全面迁移到 TOML（`FLOATCTF_CONFIG` → `AppConfig`），**禁止再读环境变量**
- 静态配置从 `ctx.config` 读；动态设置从 `get_setting(&db, key)` 读（缺键报 "Setting not found:<key>"——此时检查 `seed_default_settings` 是否播种了该键）
- 改了 development.toml 需要重启 API 才生效

### 陷阱 D：启动失败（fail-fast 设计）
`bootstrap::run` 顺序：加载 TOML → 设时区 → 日志 → 连接 DB/Docker/RustFS → seed settings → 调度器 → 起服务。
启动 panic 信息会直接指明是哪个环节（如 "init rustfs failed"），先修该环节；**基础设施问题先 `mise run infra:up`**。

## 步骤 4：最小修复

- **只改根因**：一个 bug 一个修复，不做无关重构（格式化等另提交）。
- 涉及数据库的修复必须附带迁移文件（幂等 SQL + 中文注释），并应用到开发库。
- 涉及行为修改（配置默认值、权限、积分规则等），**先向用户说明影响再改**（本仓库有"诊断后批准才修复"的协作习惯）。
- 修复后：
  ```bash
  cargo fmt --all
  cargo check -p floatctf
  ```

## 步骤 5：回归测试

- 新增/更新单元测试覆盖该 bug（先写能复现失败的测试，再修复让它通过——"红→绿"）。
- 跑相关测试：`cargo test -p floatctf <关键词>`。
- 能冒烟就冒烟：起服务 curl 原接口确认症状消失。

## 步骤 6：提交

- 中文 message：`fix: <一句话根因与修复>`，正文简述现象与根因。
- 与格式化/文档改动分批次提交（同一改动内的小 fmt 可同批）。

## 检查清单

- [ ] 根因已定位并有证据（日志/查询/复现测试），不是猜测
- [ ] 未引入环境变量读取、未手改 entity/（改 Schema 走了迁移 + db:gen）
- [ ] **未直接修改** `migrations/` 下任何已有文件；Schema/数据修复仅通过 `db:migration:new` 追加新迁移
- [ ] 数据库修复幂等（可重复执行），带中文注释，已应用开发库
- [ ] 复现测试存在并转绿
- [ ] `cargo fmt` + `cargo check` 通过
