## 赛制一：Jeopardy（解题赛）

- 个人赛与团队赛两种模式。
- 静态 Flag 与动态 Flag。
- 动态积分衰减（分值随解题人数下降）。
- 题目实例按需启动（独立容器）。
- 实时计分板与得分趋势。
- Writeup 提交。
- 赛事公告。

## 赛制二：AWD（攻防对抗）

- 支持 2 队及以上的对抗赛事。
- 加固（hardening）与攻击（attack）分阶段。
- 选手通过 WireGuard 接入竞赛内网。
- nftables 作用域隔离。
- Flag 下发与提交。
- 一血（first blood）标记。
- 对称失分（symmetric loss）。
- 每轮结束判定（judge at end of round）。
- 暂停 / 恢复。
- 重置（带配额与罚分）。
- 封禁 / 解封（ban / unban）。
- 最终结算与 finished 锁定（final settlement / finished lockdown）。

## 赛制三：AWDP（攻防演练）

- 练习/训练 run 与正式竞赛两种形态。
- 破坏（break）与修复（fix）阶段。
- 正式轮次评测（official round evaluations）。
- 补丁提交（patch submission）。
- 分数账本（score ledger）。
- Writeup。

## helper 安全架构

- API 是 Compose 中的**非 root** 容器：`cap_drop: ALL`、`no-new-privileges`、
  read-only rootfs。
- API **不挂载 Docker socket**，也**不持有 `CAP_NET_ADMIN`**。
- 所有需要宿主特权的操作都经由 `floatctf-helper`，通过两个 Unix socket：
  - `helper-docker.sock`：Docker 策略代理（只放行受限操作）；
  - `helper-control.sock`：宿主 Host RPC。
- 宿主的 WireGuard / nftables 由 helper 独占管理。
- 宿主 `systemd` 只管理 `floatctf-helper.service` 与 Compose 生命周期
  （`floatctf-infra.service` / `floatctf.target`）；API 本身跑在 Compose 里，
  **没有** `floatctf-api.service`。

## 安装与部署

- `install.sh` **单文件自包含**：目标机无需 clone 源码。
- Compose 统一承载 API / PostgreSQL / Redis / RustFS / Caddy。
- Caddy 自动 HTTPS。
- 宿主 systemd 只负责 `floatctf-helper` + Compose stack。
- 迁移 forward-only；fresh DB 从 `merged.sql`（48 个迁移）bootstrap。
- 升级路径：重跑 `install.sh --version <V>`；既有 PostgreSQL 集群上先起 postgres、
  应用 forward-only 迁移，再部署。
- **前置条件**：`python3` **≥ 3.11**（stdlib 带 `tomllib`）。安装器在任何改动之前做能力检查，
  缺失即中止；**不**走 `pip install`。

## 运行时镜像分发（v1.0 起）

- AWD/AWDP 的三个运行时服务镜像现在通过 **GHCR** 分发（规范在线通道）：

  ```text
  ghcr.io/floatctf/awd-flagserver:<V>
  ghcr.io/floatctf/awd-judgeserver:<V>
  ghcr.io/floatctf/awdp-judgeserver:<V>      # 已扁平化
  ```

  由 tag 触发的 release workflow 以 `packages: write` 推送，**仅** tag 发布路径
  （PR / 分支 dispatch / RC 永不推送）。
- 安装器在部署前检查**精确 `<V>` ref**（`docker image inspect` → `docker pull`），
  取不到即**硬失败**；`--skip-runtime-images`（`FLOATCTF_SKIP_RUNTIME_IMAGES=1`）可降级为告警，
  供 Jeopardy-only 宿主使用。
- registry 前缀是单一事实来源：`FLOATCTF_RUNTIME_IMAGE_REGISTRY`（默认 `ghcr.io/floatctf`），
  同时用于渲染 `config/floatctf.toml` 与安装器的镜像检查。
- 离线/内网宿主仍有本地逃生通道：在有源码的机器上
  `sudo bash scripts/build-runtime-images.sh --tag <V>`（本地历史名，awdp 仍带 `infra/` 段）
  或 `--registry ghcr.io/floatctf --tag <V>`（规范名），再 `docker save` / `docker load`
  预置归档。
- 升级重跑安装器时，管理员自定义过的三个镜像设置会被保留（并告警）；只有命中已知 stock 形态的
  值才迁移到规范 GHCR 默认值；`--reset-runtime-images` / `--keep-runtime-images` 可强制。

## 可插拔前端平台

- `apps/web` 是极薄的 bootstrap 引导页；`frontends/default` 是官方前端；
  `packages/{sdk,react,frontend-runtime}` 是前端 SDK / 绑定 / 运行时契约。
- 前端制品**版本不可变**（资产以 `Cache-Control: public, max-age=31536000, immutable` 提供）。
- 通过动态设置 `FRONTEND_ACTIVE` 激活前端。
- 破窗恢复：任意页面追加 `?frontend=default`。
- 支持外部非 React 前端。

## 运维工具

- `backup.sh` / `restore.sh`：生产备份与恢复。
- 安全卸载（`uninstall.sh`）带**活跃运行时守卫**。
- `uninstall.sh --purge`：永久清除 FloatCTF 自有状态。
- `frontend.sh`：前端管理器（`list` / `info` / `install` / `remove` / `set-current` / `verify`）。
- `SHA256SUMS`：覆盖除自身外的全部**文件**产物（不含 GHCR 镜像）。

### SDK 分发

- `floatctf-sdk-<V>.tgz`、`floatctf-react-<V>.tgz`、`floatctf-frontend-runtime-<V>.tgz`
  随每个 GitHub Release 附带，逐字节确定性；`scripts/package-sdk-dist.sh` 会在旁边写
  `SDK-SHA256SUMS`。
- **npm 尚未为 v1.0 执行发布，且属可选。** 已核实的细节：三个 tarball 一起安装时用
  **npm** 可用；用 **pnpm** 目前会失败（未发布的 `@floatctf/sdk` 触发
  `ERR_PNPM_FETCH_404`），这是 pnpm 对「相互依赖的未发布本地 tarball」的限制
  （已用通用场景复现）——因此 pnpm 消费者需要先把包发布到 registry。
- `@floatctf/react` 消费方 peer deps：`react@^19`、`react-dom@^19`、
  `@tanstack/react-query@^5.66.5`；`@floatctf/sdk` 依赖 `axios ^1.11.0`；
  `@floatctf/frontend-runtime` 无依赖。
- `packages/react/dist/index.d.ts` 需要 `skipLibCheck: true`（仓库内每个 tsconfig 都已设置）。

- **AWDP：删除赛事不再泄漏宿主运行时（P-01，commit `444fe6a`）。**
  `DELETE /api/admin/events` 的运行时拆除此前**只有 AWD 分支**，删除一个已部署的 AWDP 赛事会
  永久留下 `fctf-awdp-judge-{event_id 前 12}` 容器、`fctf-awdp-{id12}` Docker 网络与
  `floatctf_awdp_{id12}` nftables ACL 表 —— 且因 `awdp_event_networks.event_id` 对 `events`
  是 `ON DELETE CASCADE`，DB 行删除后这些资源**再也无法被解析**，只能人工回收。
  现与 AWD 同构：**先只读快照 → 删行 → 按快照拆除**（实例 → judge → ACL 表 → 网络，

  回归场景已并入 `scripts/test-awdp-http-e2e.sh`。
  实测该缺陷在真实宿主上累积了 189 个孤儿 judge 容器 + 189 个孤儿网络。

## 已知限制（Known limitations）

以下为**如实记录**的限制，不美化、不夸大。已修复的项不再列在这里。

1. **真实公网域名 HTTPS 不在 RC 验证范围内（已接受，非 GA 阻塞）。**
   RC 环境没有域名/DNS/公网 TLS。已本地验证的是生产配置下的 Caddy + 其**受信任本地 CA**：
   证书链校验通过（**未使用 `curl -k`**）、HTTP→HTTPS 跳转正确、站点/API/registry/
   immutable-asset/deep-route 行为正确。产品负责人已接受该限制；
   **运维方必须在安装后自行验证真实域名**。请勿把它理解为"真实 HTTPS 已验证"。

2. **同一宿主/helper/Docker daemon 同一时刻只允许一个 FloatCTF API/控制面（运维警告）。**
   平台的部分宿主资源是**全局或固定命名**的（例如 AWD 的防火墙状态、AWDP 练习的容器与网络），
   没有按实例隔离。第二套 API（包括开发栈、RC/测试栈或第二份生产安装）会去协调这些共享资源，
   从而干扰正在运行的实例。**这一后果在实践中已被观察到过一次**（第二控制面重建了运行中实例的
   判题容器与网络，随后由平台自身恢复），属于真实风险而非理论推测。
   请在独立宿主上做开发/验证；同一宿主只跑一套控制面。

3. **Default Frontend bundle 约 4.3 MB（gzip 约 1.08 MB）**：v1.1 的优化候选，不是阻塞项。

4. **前端不支持无刷新热切换**：切换生效前端需要页面重载。

5. **没有前端 Marketplace / 包签名机制**（post-v1.0）。

6. **宿主级独占验证（B2 / B3）仍待执行。** Phase 13 的初判为 BLOCKED：agent 沙箱无 root，
   特权安装/升级/卸载/purge 未端到端执行；AWD/AWDP 宿主级完整 E2E 因唯一可用宿主已在运行
   重要生产实例而刻意未执行（这正是第 2 条限制的来源）。Phase 13.1 关闭了全部**代码可控**工作
   （B1 运行时镜像分发 / R2 对象存储 readiness / R3 Python 前置条件 / 文档），并由产品负责人
   豁免 B4。**剩下的 B2（独占宿主上的 Jeopardy/AWD/AWDP 宿主级 E2E）与 B3（普通用户 + `sudo`
   的安装/升级/卸载/purge/重装）仍需在专用独占宿主上执行**，本阶段**没有**执行它们。
   因此正确的表述是：*全部代码可控的 GA 工作已完成；剩余的是在独占宿主上执行 B2/B3。*
